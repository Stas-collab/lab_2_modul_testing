## Запуск

```bash
npm install
npm test            # усі тести (Vitest + Supertest, без реального порту й мережі)
npm start           # сервіс на http://localhost:3000 (для Postman і Newman)
npm run newman      # колекція Postman через Newman (сервер має бути запущений), звіт results/newman.xml
```

`npm test` піднімає застосунок у пам'яті через `createApp()`, тому сервер запускати не потрібно. Для `npm run newman` сервер запускають окремо командою `npm start` в іншому терміналі.

## Варіант 9: специфікація та рішення

`POST /orders` приймає необов'язковий заголовок `Idempotency-Key`. Повторний запит із тим самим ключем і тим самим тілом повертає початкове замовлення й не створює нового.

Правила, прийняті в реалізації:

- Без заголовка кожен запит створює нове замовлення, як і раніше.
- Формат ключа: 1–64 символи, лише латиниця, цифри, `-` та `_`. Інакше — `400 INVALID_IDEMPOTENCY_KEY`.
- Ключ діє в межах користувача: той самий рядок у Alice та Bob — це два різні ключі, чуже замовлення ніколи не повертається.
- Повтор повертає `201` із тим самим `Location`, тим самим тілом (`id`, `createdAt`) і заголовком `Idempotent-Replayed: true`.
- Той самий ключ з іншим тілом — `422 IDEMPOTENCY_KEY_REUSED`.
- Запит, відхилений валідацією (`400`), ключ не «витрачає»: після виправлення тіла ключ працює як новий.
- Якщо замовлення видалили, той самий ключ створює нове замовлення.

### Очікувані коди станів

| Сценарій                                     | Код | Примітка                                        |
| -------------------------------------------- | --- | ----------------------------------------------- |
| Перший запит з коректним ключем              | 201 | `Location`, без `Idempotent-Replayed`           |
| Повтор із тим самим ключем і тілом           | 201 | `Idempotent-Replayed: true`, те саме замовлення |
| Повтор з іншим тілом                         | 422 | `IDEMPOTENCY_KEY_REUSED`                        |
| Некоректний ключ (пробіли, `/`, 65 символів) | 400 | `INVALID_IDEMPOTENCY_KEY`                       |
| Без заголовка                                | 201 | нове замовлення щоразу                          |
| Невалідне тіло з ключем                      | 400 | ключ не фіксується                              |
| Без токена / підроблений токен               | 401 | `UNAUTHORIZED`                                  |
| Той самий ключ, інший користувач             | 201 | окреме замовлення                               |
| Чуже замовлення за `GET /orders/:id`         | 404 | `NOT_FOUND`, а не 403                           |

### П'ять рівнів перевірки

| Рівень | Що перевіряється    | Де реалізовано                                                       |
| ------ | ------------------- | -------------------------------------------------------------------- |
| 1      | Код стану           | усі тести, наприклад `expect(res.status).toBe(201)`                  |
| 2      | Структура за схемою | `expectSchema(res.body, orderSchema)`, `additionalProperties: false` |
| 3      | Значення            | `total = 560`; повтор повертає ідентичне тіло (`toEqual`)            |
| 4      | Заголовки           | `Location`, `Idempotent-Replayed`                                    |
| 5      | Побічний ефект      | `GET /orders` після повторів містить рівно одне замовлення           |

### Перевірки доступу

Без токена, з підробленим токеном, до чужого ресурсу (404), ізоляція ключа між користувачами (Bob не отримує замовлення Alice і не бачить його в `GET`).

## Висновки

Набір тестів на Supertest і Vitest перевіряє сервіс на всіх п'яти рівнях: код, структуру за схемою, значення, заголовки й побічний ефект. Для варіанта 9 ідемпотентність `POST /orders` доведено наступним запитом `GET /orders`: повтори з тим самим ключем не збільшують кількість замовлень. Схема із забороною зайвих полів ловить витік внутрішніх даних, який окремі твердження не помічають. Фабрика `createApp()` дає кожному тесту власний застосунок і власні дані, тому тести незалежні. Перевірки доступу (без токена, підроблений токен, чужий ресурс) виявляють дефекти безпеки, яких зазвичай немає в ручних тест-кейсах. Колекцію Postman із запитами для нового функціоналу запущено через Newman зі звітом JUnit.
