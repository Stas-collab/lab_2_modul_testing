## Специфікація варіанта 7

> Калькулятор комісії переказу: 1 % від суми, мінімум 5 грн, максимум 150 грн; для сум понад 50 000 потрібна додаткова перевірка – виняток.

Сигнатура: `calcTransferFee(amount: number): number`.

### Розбиття на вимоги (у порядку реалізації)

| № | Вимога | Помилка / результат |
| --- | --- | --- |
| 1 | Сума має бути скінченним числом більше нуля | `INVALID_AMOUNT` |
| 2 | Мінімальна комісія — 5 грн | `5` |
| 3 | Комісія — 1 % від суми | `amount * 1 %` |
| 4 | Максимальна комісія — 150 грн | `150` |
| 5 | Сума понад 50 000 вимагає додаткової перевірки | `ADDITIONAL_VERIFICATION_REQUIRED` |
| 6 | Результат заокруглюється до копійок | 2 знаки після коми |
| 7 | Половинні значення копійки заокруглюються вгору без похибки float | напр. 501,50 → 5,02 |

### Припущення (уточнення специфікації)

- Сума рівно **50 000** дозволена; виняток — лише для **строго більше** 50 000.
- Сума `0`, від’ємна, `NaN`, `±Infinity` — `INVALID_AMOUNT`. Валідність суми перевіряється **раніше** за ліміт, тому `Infinity` дає `INVALID_AMOUNT`, а не `ADDITIONAL_VERIFICATION_REQUIRED`.
- Мінімальна комісія діє і тоді, коли вона більша за 1 % (суми до 500 грн включно → 5 грн). Мінімум застосовується після заокруглення відсотка.
- Межі порогів: 500 (мінімум), 15 000 (максимум, бо 1 % від 15 000 = 150), 50 000 (ліміт).

## Продуктовий код (кінцевий стан) — `src/transfer.ts`

```ts
const FEE_PERCENT = 1;
const MIN_FEE = 5;
const MAX_FEE = 150;
const MAX_TRANSFER_AMOUNT = 50000;
const KOPECKS_IN_HRYVNIA = 100;

const toKopecks = (hryvnias: number): number =>
  Math.round(hryvnias * KOPECKS_IN_HRYVNIA);

const toHryvnias = (kopecks: number): number => kopecks / KOPECKS_IN_HRYVNIA;

const clamp = (value: number, min: number, max: number): number =>
  Math.min(Math.max(value, min), max);

function assertValidAmount(amount: number): void {
  if (!Number.isFinite(amount) || amount <= 0) {
    throw new Error('INVALID_AMOUNT');
  }
}

function assertWithinLimit(amount: number): void {
  if (amount > MAX_TRANSFER_AMOUNT) {
    throw new Error('ADDITIONAL_VERIFICATION_REQUIRED');
  }
}

/** Відсоткова комісія в копійках, заокруглена до цілої копійки. */
function percentFeeInKopecks(amount: number): number {
  return Math.round((toKopecks(amount) * FEE_PERCENT) / 100);
}

export function calcTransferFee(amount: number): number {
  assertValidAmount(amount);
  assertWithinLimit(amount);

  const fee = toHryvnias(percentFeeInKopecks(amount));
  return clamp(fee, MIN_FEE, MAX_FEE);
}
```

## Тести (кінцевий стан) — `tests/transfer.test.ts`

```ts
import { describe, it, expect } from 'vitest';
import { calcTransferFee } from '../src/transfer';

describe('calcTransferFee', () => {
  describe('валідація суми', () => {
    it.each([0, -1, -100, NaN, Infinity, -Infinity])(
      'відхиляє некоректну суму %s',
      (amount) => {
        expect(() => calcTransferFee(amount)).toThrow('INVALID_AMOUNT');
      },
    );
  });

  describe('мінімальна комісія', () => {
    it.each([0.01, 1, 100, 499.99, 500])(
      'для суми %s комісія дорівнює мінімуму 5 грн',
      (amount) => {
        expect(calcTransferFee(amount)).toBe(5);
      },
    );
  });

  describe('комісія 1 % від суми', () => {
    it.each([
      { amount: 501, expected: 5.01 },
      { amount: 1000, expected: 10 },
      { amount: 1234, expected: 12.34 },
      { amount: 10000, expected: 100 },
      { amount: 14999, expected: 149.99 },
    ])('сума $amount → комісія $expected', ({ amount, expected }) => {
      expect(calcTransferFee(amount)).toBeCloseTo(expected, 2);
    });
  });

  describe('максимальна комісія', () => {
    it.each([
      { amount: 15000, expected: 150 },
      { amount: 15000.01, expected: 150 },
      { amount: 20000, expected: 150 },
      { amount: 50000, expected: 150 },
    ])('сума $amount → комісія обмежена $expected', ({ amount, expected }) => {
      expect(calcTransferFee(amount)).toBe(expected);
    });
  });

  describe('додаткова перевірка для великих сум', () => {
    it.each([50000.01, 50001, 100000, 1_000_000])(
      'сума %s вимагає додаткової перевірки',
      (amount) => {
        expect(() => calcTransferFee(amount)).toThrow(
          'ADDITIONAL_VERIFICATION_REQUIRED',
        );
      },
    );
  });

  describe('заокруглення до копійок', () => {
    it.each([
      { amount: 777.77, expected: 7.78 },
      { amount: 999.99, expected: 10 },
      { amount: 1234.56, expected: 12.35 },
      { amount: 5000.49, expected: 50 },
    ])('сума $amount → комісія $expected', ({ amount, expected }) => {
      expect(calcTransferFee(amount)).toBe(expected);
    });
  });

  describe('половинні значення копійки (похибка float)', () => {
    // Очікувані значення пораховано вручну: 1 % від 501,50 = 5,015 → 5,02
    it.each([
      { amount: 501.5, expected: 5.02 },
      { amount: 807.5, expected: 8.08 },
      { amount: 815.5, expected: 8.16 },
      { amount: 1000.5, expected: 10.01 },
    ])('сума $amount → комісія $expected', ({ amount, expected }) => {
      expect(calcTransferFee(amount)).toBe(expected);
    });
  });
});
```

## Опис виконаних рефакторингів

**Рефакторинг 1 (цикл 3).** Було: числа `0.01` і `5` прямо в виразі `Math.max(amount * 0.01, 5)`. Стало: константи `FEE_RATE` і `MIN_FEE`. Навіщо: «магічні числа» не пояснюють, що вони означають, і їх треба змінювати в кількох місцях, якщо тариф зміниться.

**Рефакторинг 2 (цикл 5).** Було: умови `throw` у тілі `calcTransferFee`. Стало: функції `assertValidAmount` і `assertWithinLimit` та константа `MAX_TRANSFER_AMOUNT`. Навіщо: головна функція читається як послідовність кроків, а кожна перевірка має ім’я й одну причину змінюватися.

**Рефакторинг 3 (цикл 7).** Було: після зеленого кроку з розрахунком у копійках — вкладені `Math.round` / `Math.min` / `Math.max` в одному виразі. Стало: `toKopecks`, `toHryvnias`, `clamp`, `percentFeeInKopecks`. Навіщо: відокремлено перетворення одиниць, відсоткову логіку й обмеження діапазону; поведінка не змінилася, усі 32 тести зелені.

**Знахідка циклу 7 (чому знадобилася окрема ітерація).** Простий `Math.round(n * 100) / 100` з циклу 6 проходив усі тести, але для 501,50 грн дає 5,01 замість 5,02: `501.5 * 0.01 = 5.015`, а після множення на 100 виходить `501.49999999999994`. Тест із ручним очікуванням (`5.02`) виявив це одразу. Скануванням діапазону 500,5…14 999,5 знайдено 289 сум із такою похибкою. Рішення — рахувати у цілих копійках.

## Висновки

Розроблення через тестування дало передбачуваний темп: кожна наступна вимога додавала один тест і мінімальну зміну коду. Найскладніше було утримуватися від «узагальненого» коду на кроці Green і не писати наперед обробку, якої ще не вимагав жоден тест. Окрема цінність — ручний розрахунок очікуваних значень: саме він виявив похибку подвійної точності (501,50 → 5,02), яку не помітив би тест, що рахує очікування тією самою формулою. Рефакторинг на зеленому наборі виконувався без страху зламати поведінку: покриття гілок вийшло 100 % без окремого «доганяння».

## Відповіді на контрольні питання

1. **Три кроки циклу.** *Red* — написати тест, який падає через відсутню поведінку. *Green* — написати мінімальний код, що робить усі тести зеленими. *Refactor* — поліпшити структуру коду, не змінюючи поведінки, лише на зеленому наборі.
2. **Навіщо бачити падіння тесту.** Так перевіряється, що тест справді вміє падати. Щойно написаний тест може бути зеленим з двох причин: функціональність уже реалізована (тест зайвий) або тест нічого не перевіряє (хибні перевірки, порожні очікування).
3. **Чому мінімальний Green.** Щоб код з’являвся лише під вимогу тесту, а кожна його частина була покрита. Приклад: у циклі 1 функція просто кидає `INVALID_AMOUNT`; у циклі 2 — повертає константу `5`.
4. **Чому рефакторинг лише на зеленому наборі.** Зелені тести — єдиний доказ того, що поведінка збереглася. Якщо набір уже червоний, неможливо відрізнити помилку рефакторингу від існуючої несправності.
5. **У якому циклі знадобився рефакторинг.** У циклі 3 (магічні числа → константи), у циклі 5 (винесення перевірок), у циклі 7 (розділення обчислення на допоміжні функції) — див. розділ про рефакторинги.
6. **Порядок нічного тарифу й добового ліміту** (показова частина). Знижка в частках від суми і обмеження зверху — нелінійні разом: `min(a, 200) / 2 ≠ min(a / 2, 200)`. Для 600 хв: ліміт, потім ніч → 100, а ніч, потім ліміт → 200. Тому порядок — це вимога замовника, а тест його фіксує. У моєму варіанті аналог — порядок «відсоток → мінімум/максимум → заокруглення».
7. **«TDD дає зворотний зв’язок про архітектуру».** Якщо код важко тестувати (багато залежностей, змішані відповідальності), це видно відразу. У роботі: розрахунок у копійках і окремі `assert*` функції з’явилися через потребу писати прості, точні тести.
8. **Чому один коміт не зараховується.** Оцінюється доказ застосування підходу — історія «тест → мінімальний код → рефакторинг». Один коміт з готовим кодом цього не доводить, навіть якщо тести якісні.
9. **Класи задач, де TDD підходить погано.** Дослідницькі прототипи з невідомою постановкою; візуальний/UX-дизайн, де результат оцінюється людиною; код зі складною взаємодією із зовнішнім світом (апаратура, нестабільні мережі), де тести дорожчі за код.
10. **Найкращий сценарій у промисловій роботі.** Бізнес-логіка з чіткими правилами й числовими порогами (тарифікація, комісії, знижки) і виправлення дефектів: спочатку тест, що відтворює баг, потім виправлення — регресія неможлива.
